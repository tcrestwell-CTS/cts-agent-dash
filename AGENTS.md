# Project Architecture Rules
- Manual supplier receipt confirmation updates only the linked payment flag; its locked database trigger adds the actual amount to the same-trip booking, and QBO never infers bookings from trip order.
- Form-upload reads and deletes resolve ownership through the form ID path prefix and intake_forms.user_id, with role-checked staff exceptions; anonymous guest uploads have no reliable uploader identity.
- Circle briefing reads require an assigned advisor or staff role; a valid login alone must not grant access.
- Public financing and rental submissions use the existing service-side allowlisted handlers; payment IP logs are server-write-only to prevent fabricated financial records.
- Public lead and onboarding inserts require valid identity fields and initial workflow state; AI/proposal results and completed provisioning cannot be supplied by guests.
- Shared training, supplier catalogs, and MSC sync history require assigned advisor or staff roles rather than authentication alone.
- Real paid trip-payment inserts and status transitions post through qbo-sync-trigger, which resolves the trip invoice regardless of invoice creator, uses a Client Funds service item and stable QBO payment request IDs — receipts must apply once without becoming agency income.
- Bookkeeper P&L reads monthly QuickBooks ProfitAndLoss reports via the authenticated qbo-sync read-report action, never client receipt minus supplier disbursement totals — client-funds movement is not agency profit.
- QBO auth, reports and sync triggers renew through `_shared/qbo-token.ts` with conditional writes and newer-token recovery; concurrent refresh failures must not deactivate a successfully renewed connection.
- Group signup, Hawaii selections, and wizard booking emails use `_shared/group-emails.ts` with event/audience idempotency, owner-account recipients, and success/failure logs — saved submissions must not silently lose advisor or client email copies.

- Keep authenticated advisor writing assistance in the existing `itinerary-ai-action` function so itinerary and trip-page copy share one guarded AI boundary.
- RateHawk booking (hotel_page→prebook→form→finish→status) lives in `supabase/functions/ratehawk/booking.ts`; guest deposit is a Stripe client-account PaymentIntent verified server-side before `booking/finish`, and RateHawk is paid from the ETG B2B deposit — keeps supplier and guest money separate.
- RateHawk booking error/status codes live only in `supabase/functions/ratehawk/errors.ts` (sourced from ETG docs), and booking.ts classifies every upstream reply through it — one table keeps retry/terminal behavior consistent across form, finish and status.
- RateHawk post-booking (order_info, cancel_quote, cancel_booking) lives in `ratehawk/booking.ts`; order/info is source of truth for status and the guest Stripe refund is deposit × (RateHawk refunded ÷ sell) — refunds follow what RateHawk actually confirms, not cached policy.
- RateHawk certification test triggers (`test_scenario_suffix`, `debug_trace`) are admin + sandbox only in `ratehawk/booking.ts`, and form retries keep the suffix — ETG sandbox forces unknown/soldout/book_limit by partner_order_id suffix, and it must never reach production.
- RateHawk orders left "processing" are re-checked by the `ratehawk` function (x-cron-token from `private.cron_tokens`) via a pg_cron job armed by a status trigger and unscheduled when none remain; a per-order DB lease (`claim_ratehawk_status_check`) serializes manual/finish/sweep checks, and after 6h an order is flagged needs_attention — no idle polling and no double status calls.
- RateHawk advisor UI: `RateHawkBookingDialog` (search → prebook → form → Stripe deposit via `create-flight-payment-intent` → finish/status) and `/hotels/orders` call only the `ratehawk` function through `src/lib/ratehawkApi.ts` — the backend stays the single source of booking rules and error text.
- Group booking wizard: public `/group/:token/book` talks only to the `group-booking` function, which re-prices server-side via `_shared/group-pricing.ts` (byte-identical to `src/lib/groupPricing.ts`, enforced by test) and charges deposits on the client Stripe account (`STRIPE_SECRET_KEY_CLIENT`); the webhook's `group_deposit` branch writes the paid trip_payments row — one pricing source, and group money stays on the client account.
- Onboarding e-signature documents (IC Agreement, Code of Ethics, Media Release, Data Consent) are all generated by `generate-signed-ic-agreement`, one PDF + one `signed_documents` row per signed document (document_type = checklist key) — one boundary keeps signing rules and legal text in one place.
- QBO per-advisor attribution lives in `supabase/functions/_shared/qbo-advisor.ts`: invoices and payout expenses carry the trip owner's QBO Class, and payouts use the advisor's mapped vendor as payee — one helper keeps attribution consistent across sync paths.
- QBO advisor payout expenses are paid from the bank account mapped to role `advisor_payout_bank` in `qbo_account_mappings` (currently Bluevine Checking), falling back to the "Advisor Payouts Clearing" liability account when unmapped — keeps the funding account configurable without code changes.
- qbo-sync-trigger resolves the QBO connection by record user_id, falling back to the single active agency-wide connection — advisor-owned records (e.g. agent_subscription_payments, keyed by agent_user_id) post to the agency's QBO company, not a per-advisor one.
- Client refunds post once through qbo-sync-trigger `client_payment_refunded` (trigger_qbo_client_payment): a full or partial Stripe refund writes one QuickBooks refund receipt against client funds and stores the id on trip_payments.qbo_refund_id — refunds reduce the client-funds liability and never touch P&L.

- Cabin price_period `cabin` stores a whole-room trip fare in price_per_person; signup and shared wizard pricing charge it once, while deposits remain per traveler — prevents multiplying cabin quotes by occupancy.
- Celebration-specific presentation is scoped by the landing page's theme class with semantic CSS tokens; shared signup and RSVP behavior stays unchanged so visual refreshes do not affect other groups.
