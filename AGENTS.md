# Project Architecture Rules

- Keep authenticated advisor writing assistance in the existing `itinerary-ai-action` function so itinerary and trip-page copy share one guarded AI boundary.
- RateHawk booking (hotel_page→prebook→form→finish→status) lives in `supabase/functions/ratehawk/booking.ts`; guest deposit is a Stripe client-account PaymentIntent verified server-side before `booking/finish`, and RateHawk is paid from the ETG B2B deposit — keeps supplier and guest money separate.
- RateHawk booking error/status codes live only in `supabase/functions/ratehawk/errors.ts` (sourced from ETG docs), and booking.ts classifies every upstream reply through it — one table keeps retry/terminal behavior consistent across form, finish and status.
- RateHawk post-booking (order_info, cancel_quote, cancel_booking) lives in `ratehawk/booking.ts`; order/info is source of truth for status and the guest Stripe refund is deposit × (RateHawk refunded ÷ sell) — refunds follow what RateHawk actually confirms, not cached policy.
- RateHawk certification test triggers (`test_scenario_suffix`, `debug_trace`) are admin + sandbox only in `ratehawk/booking.ts`, and form retries keep the suffix — ETG sandbox forces unknown/soldout/book_limit by partner_order_id suffix, and it must never reach production.
- RateHawk orders left "processing" are re-checked by the `ratehawk` function (x-cron-token from `private.cron_tokens`) via a pg_cron job armed by a status trigger and unscheduled when none remain; a per-order DB lease (`claim_ratehawk_status_check`) serializes manual/finish/sweep checks, and after 6h an order is flagged needs_attention — no idle polling and no double status calls.
- RateHawk advisor UI: `RateHawkBookingDialog` (search → prebook → form → Stripe deposit via `create-flight-payment-intent` → finish/status) and `/hotels/orders` call only the `ratehawk` function through `src/lib/ratehawkApi.ts` — the backend stays the single source of booking rules and error text.
- Group booking wizard: public `/group/:token/book` talks only to the `group-booking` function, which re-prices server-side via `_shared/group-pricing.ts` (byte-identical to `src/lib/groupPricing.ts`, enforced by test) and charges deposits on the client Stripe account (`STRIPE_SECRET_KEY_CLIENT`); the webhook's `group_deposit` branch writes the paid trip_payments row — one pricing source, and group money stays on the client account.
